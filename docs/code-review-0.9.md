# HLS AES-128 implementation review

Date: 2026-10-21. Source review and regression evidence for ordinary HLS identity AES-128; this is not DRM support or a complete media compatibility claim.

The implementation follows the full-segment CBC/PKCS7 scheme, IV rules and initialization requirements in [RFC 8216 sections 4.3.2.4–5.2](https://datatracker.ietf.org/doc/html/rfc8216#section-4.3.2.4). Media playlists retain each part's key address and explicit 128-bit IV or derive the IV from its safe integer media sequence. Encrypted initialization requires an explicit IV. Key rotation and METHOD=NONE transitions preserve their exact positions in the plan. Invalid/empty formats, sample encryption and DRM formats are refused; no license requests or protection removal occurs.

| Review finding                                                                                    | Resolution and evidence                                                                                                                                                                                                                                                                                                                                                                                                                          |
| ------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Keys introduce another request origin and potentially sensitive payload.                          | Key URLs use the ordinary validated public-request/redirect/permission path, without cookies/referrers/headers from the page. Review includes key origins. Actual Chrome refuses an ungranted key CDN before fetching encrypted initialization.                                                                                                                                                                                                  |
| Raw keys must not become durable checkpoints or accumulate in a cache.                            | Read exactly 16 bytes, import a nonextractable Web Crypto decryption key, clear the raw buffer and retain only a SHA-256 fingerprint in the source checkpoint. No key cache, raw key database field, diagnostic payload or exported key is added. Clearing buffers is best effort, not a forensic-erasure guarantee.                                                                                                                             |
| Resume could combine retained plaintext with an altered key/source.                               | Revalidate each completed key fingerprint and ciphertext source identity before requesting missing payload. Changed key refusal preserves completed output; restoring the key allows a correct continuation. Strong validators permit HEAD-only ciphertext revalidation, while weak validators compare ciphertext bytes.                                                                                                                         |
| Ciphertext size differs from decrypted and converted output.                                      | Persist separate ciphertext bytes/hash and output extent/hash. Padding validation and container/timeline validation precede the normal flush/checkpoint commit. Invalid key lengths and padding produce no checkpoint for the failed logical part.                                                                                                                                                                                               |
| Keeping one array per network chunk could exhaust memory despite a byte cap.                      | Accumulate into fixed 256 KiB blocks with at most 65 blocks, independent of network chunk count. Web Crypto operates on one bounded logical part, never the entire presentation. Encrypted plaintext is capped at 16 MiB, with up to 16 padding bytes; initialization retains its 1 MiB plaintext cap. A tiny-chunk test crosses block boundaries and verifies exact plaintext. Total browser-process peak memory is not measured by this bound. |
| Clearing decrypted input after push could invalidate bytes retained by the TS parser until flush. | Keep the input alive until conversion finishes, then clear it in the receive cleanup. This bug was found by byte-for-byte comparison with the clear TS path; the regression now requires equal output for both containers.                                                                                                                                                                                                                       |
| A key-only allowance pause could repeat forever when a full part plus verification cannot fit.    | Charge key bytes to the same throttle/allowance path. Require the part, its key and retained-key verification overhead to fit one complete allowance; otherwise report an actionable configuration error. A boundary regression verifies no partial output is committed.                                                                                                                                                                         |
| Key fetch/decryption failures must release network and conversion resources.                      | Key streams use existing timeout/abort handling. A partial key stream is canceled on abort. Native bounded Web Crypto work checks cancellation before and after completion; no output commits after cancellation. Child conversion and main OPFS cleanup retain their existing ownership boundaries.                                                                                                                                             |

The development fixture encrypts the project's own MP4/TS samples using Node's independent AES-CBC implementation. Runtime uses Chrome Web Crypto only, with no new library or manifest permission. Tests cover encrypted initialization, rotated keys, explicit and sequence IVs, clear transitions, exact/implicit byte ranges, full-browser recovery, exported encoded-sample identity and independent color/audio/seek decoding.

CBC does not authenticate media or its publisher. A valid padding block, structural validation and locally computed checksum do not prove authenticity; an independently trusted expected digest remains useful. Public unsigned keys and media can be changed by their server. Ordinary HTTP, DNS rebinding, signed URL secrecy, visible-manager lifetime and destination-consent limitations remain as documented in [security](security.md).

Separate audio/languages, continuous TS without independently decodable boundaries, other ordinary encryption methods, discontinuities, live recording, DASH, site crawling and localization remain open in the [capability audit](feature-parity.md).
