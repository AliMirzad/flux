# Flux limitations

As of 2026-10-21, these constraints define the supported design. Build/test evidence may impose additional limits.

- Keep the manager tab open during Flux engine transfers. Closing, discarding, reloading, or crashing it stops its worker. Durable completed ranges can be recovered; the current unfinished range can require retransmission. Linked original browser transfers can continue with Chrome open and remain controlled through the popup. Sleep and full shutdown prevent transfer.
- Acceleration requires a stable, compatible HTTP server with correct byte-range responses. More requests can provide no benefit or trigger throttling. No speed multiplier or superiority over IDM is promised.
- Public GET URLs are the primary target. Redirects are followed only after validating the next destination and its permission. An explicit cookie choice permits the browser session only on the original source origin; other origins and imports omit credentials. Browser policies can still block authentication; referrer-bound URLs, POST downloads, and DRM remain outside the transfer engine; those retain the website's ordinary Chrome download. Approved blob/data files up to a conservative 1 GiB cap can pass through bounded messages into verified local staging; they cannot be re-downloaded or repeated. An interrupted ingestion must be recreated on its website. The cap is not proof of large page-file memory usage or capacity. HLS assembly supports completed H.264/AAC renditions with muxed tracks: fragmented MP4 or independently decodable MPEG-TS parts, clear or ordinary identity AES-128 CBC/PKCS7. Separate video/audio/language choices are supported for completed fMP4 renditions only, with strict timing/alignment checks. TS requires supported single-program metadata, video access-unit delimiters and keyframe starts; each source part is capped at 16 MiB. Encrypted plaintext parts are also capped at 16 MiB, initialization at 1 MiB; keys require public website access and resume revalidation. Continuous non-keyframe TS, split program sections, separate TS tracks, other encryption methods, discontinuities, live recording and DASH remain unfinished engineering work.
- Resume requires compatible range support and a trustworthy resource identity. Changed or unverifiable resources must restart safely. Signed URLs can expire.
- Automatic capture requires explicit enabling and website access. Recognized link clicks go straight to Flux. An observed native download can transfer ownership only for a recent unambiguous GET with a successful source-session-aware probe and durable Flux job; otherwise Chrome retains it and Flux can show its original browser-transfer row. Native events arrive after transfer begins, so zero browser bytes cannot be guaranteed on that path. Chrome-managed rows do not use Flux connection limits, bandwidth/allowance controls, queue schedules or SHA-256 verification. They do not silently replay a POST. Generic generated downloads with ambiguous parent attribution are skipped when exclusions exist; trusted blob/data download links use verified page attribution. Data URLs without a public page attribution are not tracked.
- Scheduling is best effort while Chrome and the manager run. Alarms can reopen the manager while Chrome is running, with best-effort delivery. Device sleep, missing alarms, tab lifecycle, and user permissions can delay it.
- Allowance limits apply to authorized Flux payload, not all network traffic. Range reservations and up to 1 MiB of unused shared credit can conservatively overcount interrupted work; browser buffers, probe bytes, headers, Chrome-managed transfers and other apps are outside the counter. Non-resumable files larger than a whole allowance require a higher limit. Periodic queues retain earlier copies and therefore use additional disk space.
- OPFS stages bytes inside the Chrome profile. Export uses Chrome's Downloads folder by default or an explicitly chosen folder/Save As destination, and requires another disk copy. A folder selected once can receive verified files automatically; Chrome can require renewed permission. Numbered suffixes avoid collisions among Flux's serialized saves; the filesystem API cannot provide an exclusive-create transaction against other apps changing the same folder concurrently. Storage estimates do not reserve space; quota exceptions, disk exhaustion, user deletion, profile damage, and uninstall can destroy local data.
- Multi-gigabyte architecture is not a verified capacity claim. 100 MB, 1 GB, 5 GB, and 10 GB require separate complete download, checksum, export, memory, and recovery evidence. Do not infer a 10 GB result from small fixtures.
- Rate limiting controls application read/write pacing. Browser/network buffering and multiplexing mean instantaneous network usage and transport connection count can differ.
- Local hashes validate consistency and optional expected digests. They do not authenticate the publisher or scan for malware.
- Blocking private address literals cannot prevent all DNS rebinding to internal networks. Users should grant access only to trusted origins; see [security review](security.md).
- Initial compatibility targets are Chrome on Windows and macOS. Other Chromium builds, Incognito, managed profiles, mobile browsers, and Firefox/Safari are not automatically supported.

Official API evidence and the selected fallbacks are in [technical feasibility](technical-feasibility.md). A successful build does not by itself prove lifecycle behavior, store approval, large-file capacity, or production readiness.
