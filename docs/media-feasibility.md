# Segmented media: feasibility and acceptance contract

Research date: 2026-10-20; implementation update: 2026-10-21. Status: **limited HLS fMP4 and independently decodable MPEG-TS VOD assembly implemented and tested; broader media work remains open**. The original requirements below remain the acceptance contract for the complete requested IDM/AB media capability.

The unreleased working tree has since added static DASH, finite muxed HLS live recording, non-keyframe TS continuation and split program tables. The historical evidence below is unchanged; see [current development scope and verification](development-features.md) for those additions.

## Source findings

[RFC 8216](https://datatracker.ietf.org/doc/html/rfc8216) defines playlists, alternate renditions, initialization sections, byte-range segments and discontinuities. MPEG-TS and fragmented MP4 need different container handling. A list of segment URLs alone does not establish a valid combined file. This supports a manifest-aware download plan rather than treating a playlist as an ordinary binary file.

[DASH-IF's timing model](https://dashif.org/Guidelines-TimingModel/) describes representation timelines and segment addressing, including numbered/time templates and initialization resources. Audio and video can have distinct timelines. Selecting and joining tracks therefore needs presentation/timescale handling; a simple template string expansion is insufficient evidence of synchronization.

The [W3C ISO BMFF byte-stream format](https://www.w3.org/TR/mse-byte-stream-format-isobmff/) describes initialization and media boxes, fragment addressing and decoder requirements. MSE append acceptance is useful validation, but a downloadable standalone artifact also needs independent duration, seek and playback checks. Arbitrarily concatenating complete MP4 files or repeating initialization metadata is not a validated remux strategy.

The primary [mux.js documentation](https://github.com/videojs/mux.js/blob/main/README.md) describes MPEG-TS-to-fragmented-MP4 conversion, combined output, timestamps and initialization data. Version 0.8 bundles a pinned, locally patched subset after checking its license, source hashes, worker/CSP behavior and standalone output. Its support is restricted to the tested subset below; arbitrary HLS/DASH export and separate TS audio need further implementation. Separate fMP4 composition was added in 0.10 with the bounded acceptance below.

## Required implementation

1. Discover and review public manifest sources under existing capture/host rules. Offer quality, audio/language and output choices. Do not silently turn a detected manifest into an engine download or mistake a playlist file for the finished video. Live recording requires a separate finite stop policy; VOD and live acceptance must be distinguished.
2. Parse a bounded manifest and resolve each child URL against its actual validated response URL. Apply the source-origin session choice (other origins omit credentials), scheme/private-address, redirect, host-grant, downgrade and loop controls to child playlists, initialization resources and media segments. No arbitrary page JavaScript, cookie scraping, DRM license requests or remote processor is part of this design. Ordinary supported non-DRM encryption requires explicit format/key handling and its own tests, rather than a blanket claim that all encryption is DRM.
3. Persist a selected rendition/track plan, ordered timing/byte-range metadata, immutable plan identity and completed logical-segment checkpoints. Reopening must revalidate both plan identity and stored bytes. Changed plans, initialization sections, codecs or discontinuities need a demonstrated safe merge strategy or an actionable refusal retaining valid partial data.
4. Run container parsing/remuxing in the visible manager's worker. Stage/export through OPFS and File System Access with bounded buffers and backpressure. Feed every payload through bandwidth/allowance controls. Bound per-segment parser state, not just fetch read buffers. Cancellation must abort all outstanding requests and release handles. Integrate transient failures with the 0.6 bounded retry policy without inventing byte-range identity for different segment URLs.
5. Produce an ordinary playable media artifact with correct track metadata and timing. Test separate audio/video, muxed renditions, range-addressed media, alternate audio, missing segments, timestamp gaps, changed resources and long timelines. MP4 hash success alone cannot prove that the output decodes, seeks or stays synchronized.

## Evidence needed before a support claim

Use deterministic, redistributable media fixtures with known visual/audio markers and expected duration. Exercise actual Chrome playback of the exported file, decoded frames, audio presence, start/middle/end seeking and A/V alignment; supplement with an independent container inspection. Test pause/reload/resume, a failed segment after a committed checkpoint, cross-host permission refusal, corrupt segments, storage exhaustion and bounded memory under long/large workloads. Preserve exact input/output fixture hashes and the tested support matrix.

Native tools may generate or inspect development fixtures if available, but the shipped extension must not depend on one. Keep all runtime JavaScript/WASM packaged locally and audit any added dependency. The no-helper/no-backend constraints remain unchanged.

The fixture is locally synthesized H.264/AAC MP4 with three colors and oscillator tones, not third-party media. The actual extension reviews a master playlist, stages its rendition, exports through Save As and then an ordinary Chrome page decodes the exported bytes. SHA-256 matches the independent fixture. Duration is 4.0832 seconds, dimensions 160×90; seeks at 0.5/2/3.5 seconds decode red/green/blue, and decoded audio windows contain 440/880/1320 Hz with RMS above 0.04. Audio duration differs from video by under 0.2 seconds. Exact values are preserved in [playback proof](hls-playback-proof-0.7.json). This is short muxed-rendition evidence; separate tracks, long timelines, sustained memory and all-codec claims do not follow.

MP4 initialization and fragment metadata are each capped at 1 MiB, manifests at 4 MiB and plans at 32,768 parts. Runtime payload is streamed in bounded chunks into OPFS; initialization/sample metadata is inspected without loading all frames into memory. Limits are conservative parser boundaries, not a measured total-process-memory guarantee.

The 0.8 TS output is independently decoded and seeked in Chrome with the same colors, tones and 4.0832-second presentation. Every encoded video frame and AAC sample matches the source (62 and 185 respectively). Source and converted output bytes have distinct checkpoints; full Chrome restart retains the first converted part and revalidates its source without replay. Malformed AAC produces no completed part and does not block the next job. Packet continuity/CRC, cancellation/deadline and 33-bit clock-wrap regressions pass. See [0.8 verification](verification-0.8.md) and [review](code-review-0.8.md).

The 0.9 AES fixtures use an independent development cipher to encrypt those same MP4/TS samples. Actual Chrome exports have exactly the clear-path output hashes and encoded samples, with the same independently decoded markers. Both recover through full Chrome restart without replaying retained ciphertext. Key-origin refusal, changed key, invalid key/padding, allowance boundaries, tiny chunks, exact/implicit encrypted ranges and key-response cancellation are covered. Decryption buffers one bounded logical part (16 MiB plaintext plus up to 16 padding bytes), not the full presentation; fixed 256 KiB blocks also bound retained object count. Raw keys remain temporary. CBC is not authenticated encryption, and long-media/total-process-memory gates remain open. See [0.9 review](code-review-0.9.md) and [verification](verification-0.9.md).

## Separate fMP4 audio in 0.10

Review exposes master audio names/languages and retains the selected media playlist. Completed video-only and audio-only H.264/AAC fMP4 plans can be composed, including identity AES-128 on either source. Initialization combines track metadata, remaps colliding source track IDs to video 1/audio 2, and keeps encoded samples unchanged. Fragments retain relative sample addresses and one shared decode-time origin. Source starts must align within 0.5 seconds, each declared cumulative duration must agree with its track timeline within 0.25 seconds, and playlist durations must agree within 0.5 seconds. Gaps/overlap or unsupported layouts are refused. These are conservative admission thresholds, not a guarantee for arbitrary streams.

Both initializations and both first media fragments commit as logical pairs; recovery revalidates both members before continuing. Source identity, ciphertext/key fingerprints and output extent/hash remain distinct. A compound part plus necessary key verification must fit one allowance. Combined initialization remains at most 1 MiB, each manifest at most 4 MiB and the two plans together at most 32,768 media parts. Selected audio persists through cancel/redownload, periodic queue templates and version-3 URL-list exports.

The own synthetic fixture has separate tracks with intentionally colliding track ID 1. Original and alternate choices preserve all 62 video frames and 185 selected AAC samples. Alternate audio rotates the synthetic AAC sequence; it tests routing and timing, not spoken-language recognition. Actual exported files are independently decoded and sought in Chrome, and clear/encrypted paired jobs recover both retained sources after a full browser restart. Missing audio-origin access and weak-validator companion changes fail safely. Exact hashes, decoded tones and remaining long-media gates are in [0.10 verification](verification-0.10.md).

## Version 1 candidate expansion

The current support matrix and new playback/recovery results are in [v1 acceptance](release-acceptance-v1.md). It adds continuous TS with split PSI, separate TS audio, compatible HLS discontinuities, static multi-period DASH and bounded dynamic DASH recording. Earlier sections describe the historical 0.7–0.10 artifacts, not the current support boundary. Codec/default changes, DRM, hierarchical SIDX, dynamic DASH period switching and separate-audio live HLS remain refused.
